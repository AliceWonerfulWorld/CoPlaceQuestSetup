# CoPlace カード操作ログ追加後の8枚カード結果確定の修正

## 原因と再現比較

上限を超えたキーは NetSync の Room グローバル変数 `finalBoardAgreement`。全員の Ready と非把持状態を確認すると、先頭参加者の `FinalAgreementManager.LateUpdate` が結果を生成し、`SessionVariableTransport` のセッション付き JSON に格納する。送信前の UTF-8 検査で 1024 バイトを超過したため、上限を超えた結果は送信されなかった。

カード操作ログ追加時に共通のセッション DTO に `operation` を加えた。Unity の `JsonUtility` は未設定の参照フィールドも既定値を持つオブジェクトとして書き出した。結果確定値には `,"operation":{"id":"","deviceKey":"","client":0,"epoch":0}` が付き、58バイト増えた。カード操作タグを一度も送らない従来の配置 API でも再現する。実際の操作 UUID や端末ハッシュは結果確定値に入っていなかった。結果に含まれる32文字のカード別 revision は、配置変更や A → B → A を識別する既存の同意用 UUID。Ready は引き続き指紋を値とする。

現作業ツリーと分離した Unity プロジェクトで、同じ Scene・ProjectSettings と同じ検証3系統を使用した。カードログ追加前は HEAD `14a21af` の C#、ログ追加直後は修正着手時の C# を使った。測定用の出力は隔離コピーにだけ追加した。

| 検証 | カードログ追加前 | 追加直後・修正前 |
|---|---:|---|
| ExperimentDataManagementVerification | 140項目すべて成功 | 114項目通過後、Main Normal の確定失敗 |
| ParticipantUIVerification | 2,659項目すべて成功 | 136項目通過後、1人・A・Normal の確定失敗 |
| ExperimenterUISimplificationVerification | 215項目すべて成功 | 24項目通過後、Pilot Normal の確定失敗 |

3件はカードログ実装による本番通信形式の回帰。元の検証や8枚のテストデータに原因はなかった。以前から、旧形式の提案方式・2人の値は1,006バイトと上限に近かった。そこに既存の競合復元経路による32文字の repair トークンが加わると、同条件の計算上は1,038バイトになる。旧形式の通常送信は隔離環境で成功し、この旧形式の復元時超過は実 Room で再現確認していない。

### 修正前の値の内訳

通常方式・1人・セット A の実測例。外側は `session`、JSON 文字列としてエスケープした `value`、`repair` と、回帰時に付加された空の `operation` で構成される。

| 内側 Board の要素 | 素の JSON 内のバイト数 | 外側でエスケープ後のバイト数 |
|---|---:|---:|
| confirmed | 16 | 18 |
| sessionId | 46 | 50 |
| fingerprint | 60 | 64 |
| participants | 18 | 20 |
| readyProof | 59 | 63 |
| placements（cardId・tier・revision × 8） | 606 | 704 |
| 括弧と区切り | 7 | 7 |
| 合計 | 812 | 926 |

外側の `session` が44バイト、`repair` が11バイト、`value` のキーと文字列の引用符および外側の括弧・区切りが14バイトで、追加前は995バイト。空の `operation` と区切りの58バイトを加えて、修正前の実測は1,053バイトだった。3系統とも最初に到達した1人・通常方式でこの値を観測した。

NetSync の `NetworkVariableManager` は Global／Client 両方の**変数値単体**に `string.Length <= 1024` を適用する。シリアライザーも文字数で切り詰める実装で、その後値を UTF-8 にする。キーと送信元などは別フィールド。CoPlace の Board 送信前ガードは外側 JSON 全体を UTF-8 バイト数で検査する。測定値は ASCII なので文字数とバイト数は一致する。この検査は維持した。

## 修正

- `SessionVariableTransport.cs` で通常値・repair 値と、XR 配置タグ付き値の書き出し DTO を分離した。通常値のワイヤ形式はカードログ追加前と同じ。配置の Tier を読む既存 API は両方をデコードする。
- `FinalAgreementManager.cs` で、確定結果の値を明示的にバージョン 2 とした。内側 JSON は `v`（版）、`s`（合意 ID）、`f`（指紋兼 Ready 証跡）、`p`（参加 ClientNo）、`e`（カード ID・Tier・revision を保持する `c,t,r` の配列）。指紋と Ready 証跡は送信時に同じ値なので一度だけ格納する。受信後は既存のスナップショット表現に戻し、カード集合、Tier、revision、参加者、指紋を検証する。
- `ParticipantUIVerification.cs` で、8構成すべてにタグ付き配置とカード CSV の確認を追加した。同一 Tier の別参加者による再配置、旧形式の復元、最大幅の ClientNo を使うサイズ検査も追加した。

確定は引き続き1キーの原子的な更新。外側 Session ID と既存の Epoch・Reset・ACK によるセッション管理、提案方式の合意 ID の照合、Ready 指紋の計算、独立回答の提出・公開条件、実験の計測境界は従来どおり。新しい受信側は旧確定値と旧 Reset 値も読める。旧クライアントは v2 確定値を解釈できないため、同一 Room の PC と Quest はすべて修正版を使用する。

### 通信サイズ

セット A・B の実測値は各行で同じ。追加直後の2人および提案方式は、検証が通常方式で停止したため、追加前の実測に空タグ58バイトを加えた計算値。

| 8枚カードの構成 | カードログ追加前 | 追加直後・修正前 | 修正後 |
|---|---:|---:|---:|
| 通常・1人 | 995 | 1,053（実測） | 762 |
| 通常・2人 | 997 | 1,055（計算） | 764 |
| 提案・1人 | 1,004 | 1,062（計算） | 771 |
| 提案・2人 | 1,006 | 1,064（計算） | 773 |

修正後の提案方式・2人の例では内側 JSON が594バイト。エスケープ後の `v,s,f,p,e` が順に7、51、54、11、575バイトで、内側区切り6バイトと外側69バイトを加えて773バイト。最大幅の2つの UInt16 ClientNo と32文字の repair トークンを使用したサイズ試験は813バイト。通常の配置値はタグなし70バイト、タグ付き212バイト（差142）。`Unclassified`、32文字操作 ID、64文字端末ハッシュ、最大幅 ClientNo と Int64 Epoch の組み合わせでタグ付き値は245バイトだった。

## カードログと独立回答への影響

同意はデコード済み Tier と既存 revision を照合する。2人構成の全4試行で、片方が Ready の状態で相手が同一 Tier に再配置しても、Tier、revision、先行する Ready が維持され、その再配置が確定前最後のカード CSV 行として1件保存された。観測済みの行は確定スナップショットと同じ保存キューを通り、保存エラー時の Reset は既存のガードで拒否される。結果確定後に到着した更新や古いセッションの更新は当該セッションの操作行へ加えない。

独立回答の操作タグは送らず、結果確定値にも独立回答を載せない。公開前に相手の回答が参加者 UI や共同ボードに出ないことをオフライン検証した。これはアプリ上の公開制御の確認であり、既存の NetSync Client Variable に対する通信の機密性までは検証していない。

カード CSV は PC が観測した配置更新履歴。NetSync の送信集約、切断、確定通知より後に届いた配置など、観測できなかった操作は後から推定しない。観測中断を検出したセッションにはフェーズの中断マーカーを残す。ヘッダーだけの CSV は観測された配置が0件という意味で、実操作0件の証明には使わない。把持・解放・取消の独立イベントは取得対象外。

## 最終回帰結果

Unity 6000.3.17f1 でコンパイル成功。オフラインの Editor プレビュー端末と隔離したログ先を使用した。

| 検証 | 成功項目 | 確認内容 |
|---|---:|---|
| ExperimentDataManagementVerification | 140 | 対応確認、8枚での確定・保存、2回目への切り替え |
| ParticipantUIVerification | 2,702 | A・B × 通常・提案 × 1人・2人の全8試行、全員同意、最終回答・カード操作 CSV、旧形式の復元、過去 CSV の保持と保存失敗時の Reset 拒否 |
| ExperimenterUISimplificationVerification | 215 | 結果確定、保存、次試行案内、保存失敗・再試行 |
| ExperimentLoggerVerification | 44 | 両方式の操作観測、重複、0件ヘッダー、保全・再試行 |
| ExperimentResultVerification | 78 | 共同分類、結果確定、同一セッション再接続、Reset |
| CardDropVerification | 1,163 | Drop、配置適用、操作・表示の既存ガード |
| ProposedRevealVerification | 74 | 提出、同時公開、公開前後の操作、Reset |
| ExperimenterControlPanelVerification | 209 | 管理画面とセッション切り替えの保護 |

研究保存先の210ファイルは検証前後で SHA-256 が一致し、追加・削除もなかった。既存の Scene・ProjectSettings の未コミット差分と Package 構成も維持した。

## Quest で確認する項目

今回は実機試験を行っていない。修正版の PC・Quest で隔離した Room を使用し、8枚の通常方式と提案方式、2人の同一 Tier 再配置、同じカードの同時操作、全員同意直前の配置、切断・再接続時の結果復元、PC 側の両 CSV を照合する。とくに実 Room の配信順序や送信集約で PC に届かない操作の有無は、オフライン結果から判定できない。
